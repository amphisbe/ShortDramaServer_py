# For You 推荐功能设计方案

> 日期：2026-10-18  
> 状态：设计方案，尚未实现  
> 适用项目：ShortDramaServer_py / ShortDramaClient（ShortDrama_03）  
> 范围：短剧内容推荐，不包含 Reward、广告奖励及奖励观看任务。

## 1. 目标与范围

通过视频标签、用户有效观看时长和近期热门标签，实现简单、可解释的个性化推荐。

核心流程：

```text
短剧入库 → 后台内容分析与打标 → 分集继承标签
                                  ↓
用户播放 → 有效观看时长上报 → 用户标签权重 + 标签每日热度
                                  ↓
              喜好 60% + 热门 30% + 随机 10%
                                  ↓
                   For You 播放流与分页
```

第一版采用现有 FastAPI、Peewee 和数据库，不引入协同过滤、向量数据库或独立推荐平台。后台任务可以使用独立脚本和系统定时任务运行。

### 1.1 比例的明确含义

本方案中的 60% / 30% / 10% 是**推荐分数的组成权重**，不是每批内容的数量比例。

- 每个候选内容都计算喜好匹配分、热门匹配分和随机分，然后按总分排序。
- 不保证每 10 条恰好包含 6 条喜好、3 条热门、1 条随机。
- 随机分提供探索机会，但不保证每批必有陌生题材。
- 如果业务以后要求固定曝光比例，应改为三池按数量混排，不与本方案的评分含义混用。

### 1.2 第一版不做

- 每个分集独立建立标签体系。
- 用点赞、收藏、分享额外叠加偏好分。
- 用户自主创建标签、复杂多语言标签管理。
- 实时模型训练、复杂反作弊和跨设备匿名画像合并。

## 3. 内容标签

### 3.1 标签粒度与权重

以整部短剧为打标单位，所有分集继承所属短剧标签。每部剧选择 2～5 个标签；内容确实只匹配一个标签时允许单标签。

使用固定标签词表，每个标签有稳定编码和展示名称，例如 `ROMANCE`、`URBAN`、`FAMILY`。同义词映射到同一编码，计算不依赖展示语言。

第一版词表放在服务端配置中，不额外建立标签管理系统。

保留 `Drama.tags` 的现有展示数组；新增 `tag_weights`，按稳定编码保存权重：

```json
{
  "ROMANCE": 0.6,
  "URBAN": 0.3,
  "FAMILY": 0.1
}
```

约束：权重必须为正数，去重后归一化，合计为 1。旧标签能够映射到词表时，先按等权重转换；无法映射的进入待处理状态，不擅自创建新编码。

### 3.2 后台内容分析任务

“任务观看视频”在此指后台任务分析内容，不指用户的奖励任务。

任务流程：

1. 选取新入库或明确要求重新打标的短剧。
2. 读取标题、简介及字幕；需要视频信息时抽取代表性分集的关键帧或片段。
3. 使用内容分析能力，从固定词表选择标签并给出权重。
4. 校验编码、数量和权重，归一化后保存。
5. 失败记录原因并重试；连续失败后等待人工处理。

任务按 `(drama_id, tag_version)` 幂等执行。人工维护的结果标记为 `manual`，自动任务不得覆盖，除非明确重新提交。

内容分析提供方和调用配置在实施时接入；本方案不指定外部模型或服务。不能分析时保留已有有效标签，无有效标签的内容暂不进入 For You。

不要求完整播放全部分集，也不要求第一版具备运营后台。任务脚本与人工维护入口即可满足初期需求。

## 4. 有效观看时长

### 4.1 与播放进度分离

| 数据 | 含义 | 用途 |
|---|---|---|
| `position_seconds` | 当前媒体播放位置 | 断点续播 |
| `watched_seconds` | 本次播放会话累计有效观看时间 | 偏好与热门计算 |

跳转到第 100 秒不代表观看了 100 秒。推荐计算禁止直接使用播放位置、最大播放位置或完播标记替代观看时长。

有效观看时间按前台实际播放的经过时间累计：

- 暂停、缓冲、后台、页面不可见时不累计。
- 拖动进度条产生的位置变化不累计。
- 倍速播放按实际经过时间累计，不按媒体时间增量累计。
- 切换视频时建立新会话，避免跨视频累计。
- 客户端内部可使用毫秒计时，对外统一换算为秒。

### 4.2 上报规则

播放开始时向服务端申请 `session_id`，取得会话后开始累计有效观看时间，每 10 秒上报一次；暂停、切换视频、页面隐藏和离开页面时补报。申请失败时播放可继续，推荐计时等待会话建立，不回填建立前的观看时间。

每个会话维护递增的 `seq` 和累计 `watched_seconds`。失败后重发同一份累计值和序号，不生成新的会话。

服务端接受同一会话中更大的序号，计算：

```text
原始新增时长 = max(0, 本次累计观看秒数 - 上次已接收累计观看秒数)
```

重复序号、旧序号和累计值倒退不增加权重。序号较新的累计报告先到时，可覆盖中间报告；之后迟到的旧报告忽略。

服务端根据会话存续时间及两次接收的时间间隔限制新增量，允许少量网络抖动容差。首报也不能直接无条件接受任意累计时长。

### 4.3 重复观看贡献上限

同一用户、同一分集、同一个 UTC 自然日，计入推荐的有效观看时长最多为该集时长。跨会话累计检查此上限。

```text
最终新增贡献 = min(校验后新增时长, 当日剩余可计入时长)
```

播放进度仍可以更新；超过上限的观看不再增加用户偏好或标签热度。缺少可靠视频时长时可以保存进度和会话，但先不计入推荐贡献。

该上限用于防止循环播放无限加权，不作为观看奖励或结算依据。

## 5. 用户标签权重

用户每次产生有效观看贡献时，按视频标签权重分配：

```text
标签新增权重 = 最终新增贡献秒数 × 视频标签权重
```

例如观看 60 秒：

| 标签 | 视频标签权重 | 用户新增权重 |
|---|---:|---:|
| ROMANCE | 0.6 | 36 |
| URBAN | 0.3 | 18 |
| FAMILY | 0.1 | 6 |

加入每日衰减，避免历史偏好长期主导：

```text
间隔天数 = 距离上次权重更新时间的秒数 / 86400
当前标签权重 = 原权重 × 0.95 ^ 间隔天数 + 本次新增权重
```

写入时先衰减再累加，并更新权重时间。读取画像时对所有标签应用相同规则；仅读取时无需落库，避免重复衰减。

标签权重仅由观看贡献更新。第一版不将收藏和点赞额外折算为观看时间。

## 6. 热门标签

同一份最终新增贡献同步累计标签每日热度：

```text
标签当日热度 += 最终新增贡献秒数 × 视频标签权重
标签近期热度 = 当前 UTC 日期及此前 6 个日期的热度之和
```

热门标签按内容语言分别统计，避免不同语言的消费量互相淹没。定时任务每小时刷新最近 7 个自然日的汇总结果；小规模阶段也可直接聚合每日统计表。

用户偏好与热门数据必须基于同一份去重后贡献，不能在请求重试时重复累加。

## 7. 推荐计算

### 7.1 候选过滤

- 短剧和分集均已上架。
- 存在有效播放地址、有效标签和可靠时长。
- 按请求的内容语言筛选；第一版默认 `en`。
- 每部短剧选一个入口分集，默认第一集；第一集不可用时选最早可播放分集。
- 同一个推荐批次内不重复短剧。
- 不因看过少量内容或收藏就永久排除整部短剧。

第一版对符合条件的短剧直接计算分数；不先仅取少量热门再过滤标签，避免遗漏低播放量但高匹配度的内容。

### 7.2 归一化与公式

设用户衰减后标签权重为 `W(u,t)`，当前内容语言下的标签热度为 `Hot(t)`：

```text
p(u,t) = W(u,t) / max_t W(u,t)
h(t)   = Hot(t) / max_t Hot(t)
```

分母为 0 或标签缺失时，相应值取 0。候选短剧的标签权重为 `a(d,t)`，合计为 1：

```text
P(u,d) = Σ a(d,t) × p(u,t)
H(d)   = Σ a(d,t) × h(t)
R(d)   = 当前推荐批次内固定的 0～1 随机分

Score(u,d) = 0.60 × P(u,d) + 0.30 × H(d) + 0.10 × R(d)
```

三个分量均在 `0～1` 区间，避免原始播放量或观看秒数压过其他分量。按总分降序排列，同分按短剧 ID 固定排序。

示例：`P=0.8`、`H=0.5`、`R=0.4`，总分为 `0.67`。

### 7.3 冷启动与数据缺失

| 状态 | 推荐分数 |
|---|---|
| 偏好与热度均可用 | `0.60P + 0.30H + 0.10R` |
| 无偏好、存在近期热度 | `0.90H + 0.10R` |
| 有偏好、无近期热度 | `0.90P + 0.10R` |
| 偏好与近期热度均无 | 使用归一化累计播放量代替 H，按 `0.90H + 0.10R` |
| 累计播放量也全为 0 | 随机排序，以短剧 ID 作为同分兜底 |

第一版沿用客户端登录后进入 For You 的方式，不增加游客画像。有有效观看贡献后，下一次刷新使用新的用户偏好。

## 8. 固定批次分页

首次请求生成推荐批次，保存最多 100 个候选短剧及入口分集 ID 的排序结果，过期时间为 30 分钟。

```text
首次请求 → 计算分数并固定顺序 → 返回前 10 条
下一页   → 读取同一批次，继续向后取
下拉刷新 → 创建新批次，重新计算偏好、热度与随机分
```

游标为服务端签名的“不透明批次标识 + 偏移量”，客户端不解析。批次与当前用户、内容语言绑定。

- 翻页不重新打乱顺序，也不重新执行随机排序。
- 重试同一个游标返回相同候选位置；客户端按短剧或分集 ID 去重追加。
- 内容在批次存续期间下架时，返回前重新检查并跳过，游标记录实际扫描到的位置。
- 批次耗尽返回 `hasMore=false`；刷新后允许再次出现以前批次的内容。
- 游标过期返回 `410`，客户端清空旧列表并重新请求。
- 非法游标返回 `400`，不能静默退回第一页。

第一版将批次保存在数据库，适用于多进程部署；不依赖进程内字典保存共享状态。

## 9. 数据结构

### 9.1 现有表扩展

`dramas`：

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `tag_weights` | JSON 文本 | 标签编码到权重的映射 |
| `tag_status` | 字符串 | pending / processing / done / failed |
| `tag_source` | 字符串 | auto / manual |
| `tag_version` | 整数 | 打标任务版本 |

现有 `tags`、`category` 继续承担展示和分类用途；推荐只使用校验后的 `tag_weights`。

### 9.2 新增表

| 表 | 主要字段 | 约束与用途 |
|---|---|---|
| `user_watch_sessions` | user_id、episode_id、session_id、last_seq、reported_seconds、credited_seconds、started_at、last_received_at | `(user_id, session_id)` 唯一；记录累计值和去重状态，session 与分集绑定后不可更换 |
| `user_episode_watch_daily` | user_id、episode_id、stat_date、credited_seconds | `(user_id, episode_id, stat_date)` 唯一；跨会话实施每日贡献上限 |
| `user_tag_weights` | user_id、tag_code、weight、weight_updated_at | `(user_id, tag_code)` 唯一；存储用户偏好 |
| `tag_daily_stats` | stat_date、content_lang、tag_code、watch_score | `(stat_date, content_lang, tag_code)` 唯一；用于热门标签聚合 |
| `for_you_batches` | batch_id、user_id、content_lang、items_json、expires_at | 保存固定排序的短剧/分集 ID 列表 |

观看贡献使用小数秒或整数毫秒存储均可，实施时全链路统一，避免每次上报取整丢失小数。对外接口固定使用秒。

### 9.3 一致性与清理

一次上报中的会话推进、每日上限扣减、用户标签更新和标签每日统计必须在同一事务中提交。并发请求需使用行锁或等效的条件更新，避免跨会话突破上限。

跨 UTC 日期的报告，第一版按服务端接收日期归集，并继续受到实际时间间隔校验；不支持无限期离线补报。跨日边界不追求毫秒级拆分。

定期清理过期推荐批次及超过 30 天的观看会话。会话 ID 携带服务端可验证的创建时间，超过 30 分钟未活动的会话拒绝继续上报，客户端建立新会话，防止旧会话清理后被重放为新数据。每日用户上限记录至少保留 30 天，标签每日统计保留最近 30 天。

不额外保存每次心跳原始事件，降低存储量；如以后需要审计再增加事件明细。

## 10. 接口设计

以下三个接口均使用 `Authorization: Bearer <token>`。服务端从 JWT 确定用户，不接受任意用户 ID 作为写入归属。

### 10.1 上报观看贡献

```http
POST /api/v1/me/watch-events
Content-Type: application/json
```

```json
{
  "session_id": "<带创建时间及签名的播放会话标识>",
  "seq": 3,
  "video_id": "video_001",
  "position_seconds": 48.5,
  "watched_seconds": 25.0,
  "is_finished": false
}
```

`video_id` 固定为外部分集 ID。`episodeId` 固定为内部数据库 ID，禁止两个字段混用。

首个上报前，客户端调用同一路径的会话创建接口取得签名会话标识：

```http
POST /api/v1/me/watch-sessions
```

请求体只包含 `video_id`；响应返回 `session_id`。创建会话不产生观看贡献。

成功响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "accepted_seq": 3,
    "accepted_watched_seconds": 25.0,
    "credited_delta_seconds": 10.0
  }
}
```

重复报告成功返回当前已接受状态，新增贡献为 0。参数非法返回 `400`，身份无效返回 `401`，分集不可用返回 `404`，会话过期返回 `410`。

原有进度接口保留兼容；接入新接口的页面由新接口同时更新续播进度，避免重复请求。播放位置不能使用“历史最大位置”替代最新续播位置。

### 10.2 获取推荐流

```http
GET /api/v1/for-you?count=10&content_lang=en&cursor=...
```

首次不传 `cursor`，`count` 默认 10，范围 1～20。

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "list": [
      {
        "dramaId": "drama_001",
        "episodeId": 101,
        "videoId": "video_001",
        "title": "Example Drama",
        "playurl": "https://example.com/video.mp4",
        "duration": 90,
        "position": 0,
        "isLiked": false,
        "isFavorited": false
      }
    ],
    "cursor": "<不透明签名游标>",
    "hasMore": true
  }
}
```

示例仅展示关键字段，实际播放项应复用现有播放器所需字段，包括封面、字幕、互动统计和工具配置。接口中的 `duration`、`position` 统一为秒；Android 播放器适配层在接收时转换为原生需要的毫秒。

`isFavorited` 表示收藏短剧，不能复用表示关注作者的 `isfollow`。

## 11. 客户端行为

- 新增 For You 页面，复用现有播放器组件。
- 每批默认加载 10 条，滑到倒数第 3 条时预加载下一批。
- 同一时刻只允许一个翻页请求，追加前按 ID 去重。
- 下拉刷新创建新批次；旧请求响应不能追加到新批次，可使用页面请求代号丢弃过期响应。
- 暂停、页面隐藏、切换视频时停止有效计时并补报；恢复后重新建立计时基准。
- 推荐卡片点击“看全集”直接使用 `dramaId` 跳转，避免通过作者 ID 反查短剧。
- 点赞、收藏以接口返回状态回写；请求失败恢复原状态。
- token 失效进入现有登录流程，不使用固定测试用户兜底。
- 观看心跳失败保留当前会话累计值，短暂重试；会话失效后开始新会话，不将旧累计值带入新会话。

## 12. 实施顺序

1. **修正接入基础**：真实用户身份、JWT 校验、秒/毫秒边界、视频真实时长及播放状态恢复。
2. **建立标签数据**：固定词表、标签权重字段、旧数据转换、后台内容分析任务。
3. **建立观看贡献闭环**：会话创建、累计上报、重复去重、每日上限、用户权重与每日热度事务更新。
4. **实现推荐服务**：归一化评分、冷启动、语言过滤、固定批次及签名游标。
5. **接入客户端**：For You 页面、预加载、刷新、看全集及互动状态回写。

## 13. 验收标准

| 场景 | 预期 |
|---|---|
| 两个不同账号观看不同题材 | 标签权重独立，刷新后推荐存在差异 |
| 有效观看 60 秒，标签权重为 0.6 / 0.3 / 0.1 | 新增权重为 36 / 18 / 6 |
| 快进 100 秒，实际只播放 5 秒 | 只计入约 5 秒有效时长 |
| 暂停、缓冲、后台停留 | 不增加有效观看时长 |
| 重复报告、乱序报告、网络重试 | 不重复计入贡献 |
| 同一集多会话并发上报 | 每日累计贡献不超过该集时长 |
| 标签无效、时长为 0、内容下架 | 不进入推荐；不产生无依据的标签贡献 |
| 喜好与热门、随机均有数据 | 按 0.60 / 0.30 / 0.10 评分，不承诺条数比例 |
| 新用户没有偏好 | 使用热门和随机兜底 |
| 连续翻页和相同游标重试 | 批次顺序稳定，客户端展示不重复、不跳页 |
| 翻页期间内容下架 | 跳过不可播放内容，推进到正确扫描位置 |
| 刷新时旧请求返回 | 不污染新列表 |
| token 无效或会话过期 | 返回明确错误，不写入其他用户 |
| 打标失败或任务重复运行 | 保留有效旧结果，重复任务不重复覆盖人工标签 |

上线初期关注有效观看时长、推荐后播放率、标签覆盖率、重复曝光率和空列表比例。先验证数据准确和播放体验，再决定是否增加更复杂的推荐策略。
